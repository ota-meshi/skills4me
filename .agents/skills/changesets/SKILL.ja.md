# Changesets

[English](SKILL.md) · [リリースワークフロー](../../../.github/workflows/Release.yml)

Changesets で npm パッケージ `skills4me` のバージョンを更新する。初回は `package.json` のバージョンで公開する。

## Changeset が必要な変更

初回公開後、バージョン更新が必要な変更には同じ PR で Changeset を付ける。CLI が何を受け付け、何を表示し、どのように動くかを確認する。コマンドやオプション、既定値、出力、終了コード、スキルの配置や検出、対応環境が対象になる。内部のリファクタやライブラリの置き換えも、下の区分に沿って判断する。

テスト、fixture、CI、コメント、文書、リポジトリのスキルだけの変更には、通常 Changeset は不要。

## バージョンの上げ方

- `major` は互換性を壊す変更。CLI のオプション削除や、対応する Node.js のバージョンを減らす変更が該当する。
- `minor` は機能追加、リファクタ、ライブラリの置き換え。
- `patch` はクラッシュやスキルの誤検出などの不具合修正。

`skills4me` 自体への影響で判断する。依存先の更新番号や Changeset の有無には左右されない。複数の区分に当てはまる場合は、最も大きい区分を使う。

## 項目の書き方

`.changeset/<短いケバブケースの名前>.md` を作り、front matter に `skills4me` を指定する。

```md
---
"skills4me": patch
---

Reject an empty checkout path before attempting to place links.
```

本文はそのまま変更履歴とリリース PR に載る。利用者はこれを読んで更新するかを決める。

### 一つの項目に入れる変更

- 利用者が一言で説明できる変更を一つずつ書く。独立した変更は項目を分ける。複数のコマンドに及ぶ同じ修正は一つにまとめる。
- すでに記録した未公開の変更を広げる場合は、その項目を更新する。

### 利用者に伝わる書き方

- 本文は英語で二文までにする。`Add`、`Report`、`Reject` など、変更を示す動詞から始める。利用者に対応が必要な場合に二文目を使う。互換性を壊す変更では、コマンドや設定をどう直すかを先に書く。
- CLI に出てくる用語を使う。関係するコマンド、オプション、パスはバッククォートで囲む。出力が変わる場合は、変更前と変更後の例を一つ示す。入力によって出力の変化が二方向に分かれる場合は、方向ごとに一つ示す。
- 変わらないケースに触れるのは、利用者が不具合だと受け取る恐れがある場合や、対応が必要な場合に限る。実装やレビューの経緯は省く。内部のリファクタやライブラリの置き換えを記録するときは、CLI の挙動が変わったと読めないよう、実際の変更を書く。

## PR を作成・更新する前の確認

`origin/main` があれば、`npm exec -- changeset status --since=origin/main --verbose` で更新区分と、それに含まれる項目を確認する。`--since` で拾うのはステージ済みかコミット済みの Changeset なので、未追跡の項目はファイルを直接読む。Changeset が見つからないと表示された場合も、PR の差分を見て必要性を判断する。

保留中の項目を変更履歴としてまとめて読み、重複する項目をまとめ、独立した変更を含む項目を分ける。リリース対象の変更が揃い、更新区分と説明が適切かを確認する。
